# Базовая аналитика CaseGo

## Что считаем

- Только авторизованные аккаунты. Анонимные посещения, источники трафика и конверсия посетителя в регистрацию пока не измеряются.
- `visit`: страница открыта в видимой вкладке после подтверждения аккаунта.
- `collection_view`: видны как минимум 50% заголовка «Моя коллекция» в активной вкладке. Само получение данных не является просмотром.
- Первое открытие: самый ранний сохранённый результат в `openings`, а не клиентский клик или конец анимации. Повтор одного запроса не создаёт новое открытие.
- Активный пользователь дня: уникальный аккаунт с визитом, просмотром коллекции или сохранённым открытием.
- D1/D7: доля пользователей когорты первого открытия, активных ровно на следующий/седьмой календарный день UTC. Это не скользящие 24/168 часов и не «вернулся когда-нибудь за неделю».
- В знаменатель попадают только когорты, для которых целиком закончился соответствующий день наблюдения. Отсутствие созревшей когорты отображается как «—», а не 0%.
- Когорты включают только пользователей с первым открытием после применения `004-analytics`. Старые игроки учитываются в дневной активности, но не становятся новыми игроками после включения аналитики.
- Отчёт показывает до 30 последних календарных дней UTC. Сегодняшние счётчики неполные. Общий D1/D7 взвешивается по количеству пользователей, а не усредняет проценты дней.

## Хранение и надёжность

В `analytics_daily` только внутренний UUID аккаунта, день UTC и тип события. Это привязанные к аккаунту данные, не анонимная аналитика.
Email, Telegram ID, имя, IP, User-Agent, URL, реферер и содержимое коллекции в таблицу событий не копируются.
Внешние аналитические SDK, cookies аналитики, localStorage и трекинг до входа не используются.
Удаление аккаунта каскадно удаляет его события. Автоматической очистки старых событий пока нет.

Сервер выбирает пользователя из сессии, день — по часам PostgreSQL; принимает только два разрешённых события.
Уникальный ключ `(user_id, day, event)` ограничивает хранение двумя строками на аккаунт в сутки, включая повторные запросы,
вкладки и веб/Telegram. Клиентская дедупликация — только оптимизация: при пересоздании компонента запрос может повториться.
Origin сверяется с настроенным `APP_ORIGIN`, а не внутренним URL за proxy. Для локального сервера задайте его фактический
адрес и порт; для production — канонический публичный адрес сайта. Проверка Origin и ограничение тела 32 байт защищают приёмник. Это не полноценная защита от автоматизированных запросов
с валидной сессией: перед масштабированием потребуется инфраструктурный rate limiting.

`POST /api/activity` — отдельный Route Handler, чтобы не вставать в последовательную очередь игровых Server Actions.
Ошибка аналитики не меняет авторизацию, результат открытия или интерфейс игры. Отправка ограничена 5 секундами на клиенте;
неудачная попытка может повториться при фокусе/появлении коллекции не чаще раза в минуту. На смене дня активная вкладка
записывает новый день; скрытая — только после возвращения. Фоновый таймер не доказывает внимание пользователя.
Без сети, при блокировке запросов, отключённом JS или отсутствии IntersectionObserver возможен недоучёт визитов/просмотров.
Данные открытия остаются серверными. Платформенного разделения и исключения аккаунта разработчика пока нет.

## Запуск и отчёт

1. Применить `bun run db:migrate` к нужной БД. В настроенном production build Vercel эта команда уже выполняется после сборки.
2. Задеплоить приложение. Ни нового провайдера, ни ключей не требуется.
3. С `DATABASE_URL` нужной БД запустить:

```sh
bun run analytics:report
bun run analytics:report --json
```

Скрипт читает `.env.local`/`.env` по обычным правилам проекта; существующая переменная окружения имеет приоритет.
Он выполняет только read-only транзакцию и выводит агрегаты без идентификаторов пользователей. Публичного HTTP-отчёта нет.
Если локальный URL указывает на тестовую БД, отчёт будет тестовым, не production. Не публикуйте строку подключения.
На первом дне D1/D7 ещё не появятся; D1 впервые доступен после завершения следующего дня, D7 — седьмого.

## Проверки

`bun run test` — серверные правила и расчёты. Для интеграционных тестов задать `TEST_PG_SOCKET` точным Unix-сокетом
отдельной тестовой PostgreSQL с БД `cases_test`. Новые тесты создают и удаляют только собственные временные схемы.

`bun run test:analytics` и `ANALYTICS_TEST_BROWSER=webkit bun run test:analytics` — изолированные браузерные тесты
видимости, прокрутки, смены дня, дедупликации, ошибки сети, повторной попытки и очистки наблюдателей. Запросы перехвачены,
внешняя сеть, настоящая БД и работающий сервер не нужны.

`bun run test:browser` с локальными `CASE_TEST_BASE_URL` и `TEST_PG_SOCKET` дополнительно проверяет настоящую страницу,
сессию, маршрут событий, отчёт и открытие. Запускать только против отдельного dev-сервера, подключённого к `cases_test`.

Перед приглашением тестировщиков нужно объяснить сбор активности в пользовательской информации о данных;
короткое уведомление на странице не заменяет полную политику обработки данных.
