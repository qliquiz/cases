# Единый аккаунт: веб и Telegram

## Решение

Один внутренний UUID в `app_users`; внешние способы входа находятся в `identities`. Email и Telegram — способы
подтвердить владение аккаунтом, а не отдельные платформенные учётки. История, коллекция и лимит в десять открытий
относятся к UUID.

В текущем тестовом режиме вошедший пользователь может неограниченно восстанавливать 10 попыток кнопкой «Сбросить лимит».
Это серверная операция с блокировкой той же строки аккаунта, что и открытие. История, предметы и ключи повторов сохраняются.
Миграция `005-opening-limit-reset` хранит день UTC и число уже учтённых открытий на момент последнего сброса;
прошлые сбросы не переносят дополнительные попытки в новый день. Не применять этот режим как антиабьюз-ограничение.

Первый успешный вход автоматически создаёт аккаунт. В Mini App используется подписанная `initData`, на сайте — Telegram
OIDC или код из письма. На сайте можно играть без Telegram. Для общей коллекции войди существующим способом и привяжи
второй в блоке «Ваш аккаунт». Привязка требует действующей сессии плюс подтверждение новой личности. Совпадение имени
никогда не объединяет аккаунты. Если личность уже занята другим аккаунтом, привязка отклоняется; автоматическое слияние
и отвязка в этот релиз не входят. Несколько отдельных аккаунтов всё ещё могут иметь отдельные лимиты — защита от
массовой регистрации требует отдельного антиабьюз-слоя.

## Настройка

Переменные берутся из `.env.local` (пример: `example.env`), не имеют префикса `NEXT_PUBLIC_` и не должны попадать в Git.

- `DATABASE_URL`: PostgreSQL.
- `APP_ORIGIN`: канонический адрес сайта без пути, в production обязательно HTTPS.
- `AUTH_SECRET`: случайный секрет минимум 32 символа для HMAC email-кодов. Например, `openssl rand -base64 32`. Замена
  секрета инвалидирует текущие коды.
- `TELEGRAM_BOT_TOKEN`: проверка Mini App; не заменяет OIDC client secret.
- `TELEGRAM_CLIENT_ID`, `TELEGRAM_CLIENT_SECRET`: из BotFather → Login Widget. Зарегистрируй origin сайта и точный
  redirect URI `https://your-domain/auth/telegram/callback`. Используется алгоритм RS256 (настройка по умолчанию).
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`: данные провайдера почты. Порт 465 — TLS,
  остальные — обязательный STARTTLS. Настрой подтверждённый адрес отправителя и SPF/DKIM/DMARC по инструкции провайдера.

Email-вход требует только PostgreSQL, AUTH_SECRET и SMTP; бот для него не нужен. Для запуска Mini App укажи HTTPS-адрес
в BotFather. После настройки выполни `bun run db:migrate` и запусти приложение.

## Защита и ограничения

- Email-код: шесть цифр, десять минут, пять попыток на challenge, одноразовое подтверждение. Сохраняется HMAC, а не код.
  Challenge связан с HttpOnly-cookie и аккаунтом, из которого запросили привязку.
- Новый код инвалидирует старые коды этого email. Отправка не чаще раза в минуту, максимум пять в час на адрес и сто в
  час на весь сервис. Это стартовые ограничения; общий бюджет ограничивает расход, но не заменяет CAPTCHA и ограничения
  на доверенном reverse proxy.
- Не различаем в форме, существует ли email. Код не возвращается клиенту и не логируется. При сбое SMTP challenge
  инвалидируется.
- Telegram OIDC: серверный обмен authorization code, PKCE S256, одноразовый state, привязанный к HttpOnly-cookie, срок
  десять минут. Проверяются подпись JWT, issuer, audience, exp, iat и Telegram profile id. Поле `sub` не считается
  Telegram user ID.
- Сессии: случайные HttpOnly-cookie, Secure в production, SameSite=Lax, тридцать дней; в БД SHA-256 токена. До пяти
  сессий на аккаунт. «Выйти» отзывает текущую сессию на сервере. В Mini App повторное открытие снова может автоматически
  войти через Telegram.
- Коллекции двух уже созданных аккаунтов не объединяются. Лимит расходуется на общем UUID и проверяется транзакционно.
- Просроченные email challenges и OAuth flows очищаются при новых запросах; для большого production нужна периодическая
  очистка и мониторинг доставляемости/лимитов.

## Проверка

### Диагностика Telegram callback

Факт разрешения входа в Telegram ещё не подтверждает успешный серверный обмен кода и создание сессии CaseGo.
Получен production-лог `token_verify / failed`: обмен кода завершился, ошибка возникла при проверке токена или профиля.
27 сентября воспроизведён такой же лог на корректно подписанном тестовом токене со строковым `id`:
`Number.isSafeInteger` отклонял строку. Исправлено: после криптографической проверки принимается положительный безопасный
целый ID числом либо канонической десятичной строкой (без пробелов, ведущих нулей, знака и экспоненты).
Оба формата дают один Telegram subject и тот же существующий аккаунт Mini App. `sub` не подменяет `id`.
Это воспроизведённая несовместимость, а не доказанный формат реального пользовательского токена; нужен повторный вход после деплоя.
Проверки подписи, issuer/audience, срока, profile ID, PKCE и браузерного state не ослаблены.

Другие проверенные направления: импорт текущего публичного RSA-ключа Telegram локально успешен (это не проверка сети Vercel);
ошибки JOSE теперь классифицируются по разрешённым кодам независимо от экземпляра класса в сборке.
Ни значения полей токена, ни присланные authorization code/state не используются для диагностики.

После деплоя повторить вход и посмотреть Vercel Logs по метке `[telegram-login]`. Лог содержит только
фиксированные `stage` и `reason`, без URL, authorization code, токенов, cookie, client secret или сырых ошибок.
URL ошибки также содержит только этап (`authError=telegram_token_exchange`, `telegram_token_verify` и т.д.).

- `state / browser_mismatch`: не пришла ожидаемая cookie; начинать вход с того же канонического `APP_ORIGIN`, куда настроен callback, в том же браузере.
- `flow`: запрос просрочен, использован или изменился аккаунт в браузере. Начать вход заново.
- `token_exchange / invalid_client`: проверить именно Login Client ID/Secret, не bot token; новые переменные требуют redeploy.
- `token_exchange / invalid_grant`: проверять зарегистрированный redirect URI, срок кода и повторное использование; начать новый вход.
- `token_verify`: лог различает несовпадение `aud`/`iss`, отсутствие `id`, срок, подпись, алгоритм и загрузку JWKS.
  По-прежнему нужен RS256 в BotFather; `sub` не используется как замена Telegram user ID.
  `invalid_profile_id` означает неподходящий ID после проверки подписи; `network_error` — известную сетевую ошибку,
  `type_error` — другую ошибку типов/runtime. Строки ошибок, cause и содержимое JWT не логируются.
- `identity` или `session`: проверить миграции и доступность БД. Конфликт привязки по-прежнему показывается отдельно.

Это диагностические направления, не подтверждённые причины текущего production-сбоя. Пользовательское разрешение в
Telegram не воспроизводится локальными подписанными тестовыми JWT.

### Автотесты

Автотесты используют отдельную PostgreSQL `cases_test`, локально подписанные JWT и подмену только внешней отправки
писем/обмена кода. Реальные SMTP-доставка и согласие пользователя в Telegram требуют сквозного теста с настроенными
сервисами. Проверить: email → выход → повторный вход; Telegram web → Mini App; обе последовательности привязки; конфликт
чужого аккаунта; общий лимит после смены способа входа.

### Браузерная регрессия

`scripts/browser-smoke.mts` проверяет обычный веб без Telegram SDK, форму email, открытие при reduced motion, обновление
коллекции/остатка, отзыв сессии при выходе и OAuth redirect. Реальный Telegram OAuth перехватывается браузером до
внешнего запроса; письма тест не отправляет.

Установи Chromium командой `bunx playwright install chromium`. Запусти отдельный **dev-сервер** с `DATABASE_URL` именно
тестовой `cases_test`, `APP_ORIGIN=http://127.0.0.1:3097`, тестовыми `TELEGRAM_CLIENT_ID=1234` и
`TELEGRAM_CLIENT_SECRET=test-only` на порту 3097. Затем:

```bash
CASE_TEST_BASE_URL=http://127.0.0.1:3097 \
TEST_PG_SOCKET=/path/to/test-cluster/.s.PGSQL.55432 \
bun run test:browser
```

Тест создаёт и удаляет только свой аккаунт в тестовой базе; не запускай его против рабочей БД.

  `node_modules/next/dist/docs/01-app/02-guides/server-actions.md`, `01-app/03-api-reference/04-functions/cookies.md`,
  `01-app/01-getting-started/15-route-handlers.md`.
